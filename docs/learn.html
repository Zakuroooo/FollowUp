Chapter 1

The problem we are solving

Denise owns a small US company that repairs commercial fridges, freezers and ice machines. She has 4 technicians and gets about 15–20 new requests a week.

The problem in one line: she has enough work, but she loses jobs she already has, because requests come in from 5 places and nothing reminds her who is waiting on her.

  A["Phone call"] --> X{{"Denise's memory
+ notebook"}}
  B["Website form → email"] --> X
  C["Text message"] --> X
  D["Referral"] --> X
  E["Repeat customer"] --> X
  X -->|"busy Friday"| F["Forgot to call back"]
  F --> G["$2,000 job lost to a competitor"]

Hinglish mein: kaam ki kami nahi hai — kaam haath se phisal raha hai. Request 5 jagah se aati hai, yaad dilane wala koi nahi.

She told us exactly what she wants: "one screen — who to call today, and where each job is. Waiting on quote, waiting on their yes, scheduled, done. I don't need anything fancy." That sentence is our specification.

Chapter 2

What we built (Version 1)

Landing page

Explains the product and has a Try the demo button that signs you into a private demo account in one click.

Today

Her "one screen". Separate blocks: Emergency, New requests, Quotes to send, Follow-ups due, Ready to schedule. Plus the numbers her husband wants.

Jobs

"Where every job is" — a board by stage on desktop, stage tabs on the phone, with search.

Add job

A 15-second form for calls, texts and notebook items. Detects urgency and warns if the same phone already has an open job.

One job

Call and text buttons, the next step in one tap, reminders, undo, and the full history — which answers "did I send the quote?"

Log in / Sign up

Real accounts. Each account sees only its own jobs — the database enforces it.

Pure logic

rules.ts and triage.ts never touch the database or the internet. Time is passed in. That is why we can test them with 18 automated tests.

Server Actions

Every change (add job, move stage, log a call) is a function that runs on the server, checks the input with zod, saves, and writes a history row.

Row-Level Security (RLS) — the privacy guarantee

Every table has a rule like owner_id = auth.uid(). Postgres itself adds this filter to every query. So even if our code had a bug, it could never show Denise's jobs to another account. We tested it: a request with no login got 0 rows, and a second account got 0 rows, while the database held 13.

Hinglish mein: RLS matlab database khud chowkidaar hai. Har query mein apne aap "sirf mera data" wala filter lag jaata hai.

Why stage is a fixed list

A CHECK constraint allows only the 6 stages. A typo can never create a 7th stage that the rules don't understand.

Why a separate history table

Jobs hold the current state; job_events holds everything that happened. That is what answers "did I send the quote, and when?"

Why rules, not AI, decide the list

The list must be predictable (Denise trusts it), explainable (every item has a reason), testable (18 tests) and free (no API cost). AI is used only where language is messy — understanding a pasted text (Version 2).

Chapter 7

Urgency rules (and the safe direction)

flowchart LR
  T["Problem text"] --> K{"Urgent words?
down · not cooling · warm
leak · spoiling · emergency"}
  K -->|yes| U["URGENT (sure)"]
  K -->|no| M{"Routine words?
maintenance · annual · quote for"}
  M -->|yes| N["Not urgent (sure)"]
  M -->|no| Q["Not sure"]
  Q -.->|"Version 2"| AI["Ask the AI — it may only RAISE urgency"]
  U --> O["Denise can always override"]
  N --> O

The worst possible mistake is calling a real emergency "not urgent" — that is the lost $2,000. So the rules lean towards urgent, and the AI (Version 2) is only allowed to raise urgency, never lower it.

Hinglish mein: galti karni hi hai toh safe side pe — emergency ko normal samajhna sabse mehenga hai, isliye system "urgent" ki taraf jhukta hai.

Chapter 10

Why these tools

Next.js

Pages and server logic in one project. Deploys to Vercel in one step.

Supabase

Postgres + logins + RLS in one free service. Relational data fits jobs and their history.

Server Actions

No separate API server to build. Validation still happens on the server.

zod

Checks every form input on the server before it touches the database.

Vitest

Fast tests for the rules that decide who Denise calls.

Groq + Resend (V2)

Free, fast AI for reading texts; free email for the 7 AM list.

Chapter 11

How we used Claude Code

  1. Context first: PRD, TRD, system design, edge cases and decisions were written before any code, plus a CLAUDE.md briefing every session reads.
  2. Tools: official plugins (frontend-design, feature-dev, code-review, security-guidance), Context7 for current docs, Supabase and Vercel MCP.
  3. Small steps: database → logic + tests → actions → screens.
  4. Verify every step: types, lint, 18 tests, a production build, and every flow clicked through in a real browser at desktop and phone width.
  5. The human decides: what to build, her stage names, the rules, the safety choices. The AI writes most of the code; we review and test it.

Chapter 12

Interview questions — practise out loud

Why didn't you build technician scheduling?

She said it would be "nice later" and that leads and follow-ups are the main thing. Building it now would add screens she won't use every morning.

Why do rules, not AI, decide the call list?

The list must be predictable, explainable and testable, and it should cost nothing to run. AI is used only for messy language, like reading a pasted text.

How is Denise's data kept private?

Row-Level Security on every table. Postgres only returns rows where owner_id equals the logged-in user. We tested it: no login and a second account both got zero rows.

Why is the follow-up threshold 2 days?

Her own words: "this one hasn't heard from us in two days." It's one constant, FOLLOW_UP_AFTER_DAYS, that I'd tune with her after a week.

What happens if two people edit the same job?

The last change wins and the history shows both. For a two-person office that is enough; locking would be overkill.

How does the guest demo stay private?

Each click creates a new anonymous Supabase user with its own seeded jobs. RLS applies to it like any account.

What would you measure after a month?

Time from request to first call-back, the share of quotes followed up within 2 days, and whether she opens the app every morning. The goal is zero "$2,000 jobs gone".

What did you decide versus what did Claude Code write?

I decided what to build from the call, the stage names, the rules, the urgency safety direction and the privacy model. Claude Code wrote most of the code; I reviewed it, tested it and verified every flow in the browser.
